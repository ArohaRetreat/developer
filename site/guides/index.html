Get started

Your first integration.

Choose the right environment, request the least access you need, then make a bounded read.

1. Choose an environment

Pre-production is restricted to approved testers. Its bookings, content and credentials are isolated; its TEST emails can still reach real booking recipients. Production credentials only work in production.

API base URLs
Production   https://aroharetreat.com/api/external/v1
Preprod      https://aroha-retreat-preprod.web.app/api/external/v1

2. Create a scoped token

Sign in with Google and create an mcp-readonly token for assistant use. Choose own records, or authorized staff records if your existing role permits them. Credentials expire in 24 hours by default. Choose 1 hour, 24 hours, 7 days or Never expires. A non-expiring token stays usable until revoked, subject to current account permissions.

Only a one-way secret hash is stored. Copy the credential once into your host's secret store or a private file. Do not put tokens in source control, URLs, screenshots or chat.

3. Read your capabilities

Shell · token supplied by your secret manager
curl --fail-with-body \
  -H "Authorization: Bearer $AROHA_API_TOKEN" \
  https://aroha-retreat-preprod.web.app/api/external/v1/runtime

The response identifies the environment, contract version and allowed operation IDs. A scope never grants another guest's records or a higher host role.

4. Recover safely

Pages default to 25, maximum 50. Follow the opaque cursor only when you need another page. Mutations require a retained Idempotency-Key; versioned changes also require the resource's exact ETag in If-Match. After a timeout, retry the same operation and key instead of creating a new booking.

Manual booking for a walk-in guest

A booking manager needs reservations:manual and contacts:read with staff row access. Use POST /manual-booking-quotes with the guest’s name, own email, phone with country code, visit kind, arrival, departure and party. Private stays also choose room IDs; individual accommodation is host allocated. Day departure follows the outing date; exclusive departure follows the last included event day.

Review the returned contact, dates, price and credit discount. Then call POST /manual-bookings with only the reviewed quoteId and a stable Idempotency-Key. The server rechecks capacity, price, current manager access, customer identity and credits, confirms once and queues the actual confirmation/invoice. No Google account is fabricated and no online payment is collected. Check-in, checkout and cancellation remain separate actual stages with their own emails.

Connect a guest’s booking history

After verified Google sign-in with the booking email, call POST /me/customer-link with the own customers:link scope and a stable key. The guest portal does this automatically. It links one unclaimed operational customer to the verified account; conflicting or already-linked identities require review. History, documents, private feedback and credits resolve the current account binding. Erasure retains minimal ownership/financial history without automatically recreating contact details.

Nightly loyalty credits

Level1/Visitor earns100 credits, level2/Friend200 and level3/Family300 for each eligible completed night. Existing6/10 qualifying-stay thresholds remain. The rate is fixed at actual check-in; checkout awards distinct eligible IST nights once, across linked account records. Day visits, events, no-shows and uncompleted nights do not earn credits. No historical credits are bulk imported.

Read GET /me/loyalty and its paginated entries with loyalty:read. One credit is ₹1; credits have no expiry and no extra percentage redemption cap. Pass whole redeemCredits to a stay quote after the best tier/promotion benefit, up to the available balance and payable price. Requests reserve credits, confirmation consumes them, and cancellation/decline restores them. Expired holds stop reducing spendable balance by server time. Credit invoices distinguish credits from money received; a fully credited invoice is settled without inventing a payment.

Managers may correct a selected customer’s wallet using loyalty:adjust, a reason, stable key and the current loyalty ETag in If-Match. Credits already reserved cannot be removed. A redeemed booking rejects date changes; cancel/rebook with an explicit fresh credit decision. Confirmed no-shows retain their contracted redemption and earn no new credits.

Find records without loading a directory

POST /customers/lookups is read-only despite its HTTP method. It requires manager contact access, accepts name prefix or exact email/phone/reference in a private body, returns at most10 matches and needs no Idempotency-Key. Refine searches when more matches exist. Contact searches never belong in URLs.

Use server filters and cursors on GET /host/reservations and GET /customers/{id}/reservations. Summary totals use a read-only aggregate snapshot; stored pending filters can include elapsed holds labelled expired. Native queries are bounded by page size; this is not a guarantee of10,000 simultaneous clients.

Payments and private feedback

GET /payments is a scoped staff ledger; GET /feedback/review is manager-only. Both support exact booking-reference filtering. Record only verified payments. Cancellation voids current payable charges while retaining historical charges and payments for review; reversing a record does not transfer a refund. Feedback stays private, invites follow actual checkout by at least24 hours, and guest edits/withdrawals retain the seven-day rule.

Connect defaults to read-only access and also supports explicitly scoped CRUD tokens. Choose only the needed permissions. For writes, read the current ETag first, then use If-Match and a stable Idempotency-Key. Retry an uncertain response with the same key and original payload. Remote OAuth and service principals are not part of this release.
