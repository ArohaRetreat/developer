Scoped-token first

Identity & permissions

Access that stays bounded.

A token is a limited credential for your existing identity. It does not grant a new role or bypass ownership.

The authorization intersection

Valid token, matching environment, active grant, explicit scopes, current user status, existing host capability, resource ownership and business policy must all allow the request. A read grant cannot approve a booking. A write scope does not imply read access.

Token creation and metadata schemas describe timed and non-expiring grants.

Own and staff records

Guests read their own records. Authorized booking staff can request an all-record grant, but a viewer remains unable to mutate. Manager operations require both the correct scope and current booking-manager access. Grant revocation is checked on requests and again inside mutations.

Read-only and CRUD modes

The default read-only mode preserves seven scopes and nine operations. Scoped CRUD mode issues purpose mcp; select each needed write scope explicitly. No existing token gains new scopes or tools. Write permission also requires the current Studio module and role. Pre-production member and invitation writes remain disabled because those identities are shared with production.

Super-admins can register sponsored integration-client metadata and a scope ceiling through the API. An optional clientId binds new tokens to their human sponsor. Revoking the client or narrowing its ceiling invalidates incompatible child grants. Widening a ceiling never widens an existing token.

Token lifecycle

Default expiry is 24 hours. Timed tokens allow 1–168 hours; explicitly choose Never expires for ongoing access. The API represents this with expiresInHours: null and returns expiresAt: null. Existing tokens keep their original expiry. At most 20 active tokens per user, including non-expiring tokens. Non-expiring tokens stay valid until revoked, subject to the same live account and permission checks. Tokens are shown once and stored only as secret hashes. Account disablement, relevant sign-in revocation, token expiry and grant revocation invalidate them. Never share a token between environments.

Authenticated management endpoints
GET    /api/v1/integration-tokens
POST   /api/v1/integration-tokens
DELETE /api/v1/integration-tokens/{id}

These management endpoints accept your existing verified Google Firebase ID token. They do not accept integration tokens. Creation requires a distinct idempotency key; its cleartext result is not replayable. A repeated issuance key returns TOKEN_ALREADY_ISSUED. Normal API calls use the resulting integration token.

Privacy and deferred identity features

Managed OAuth authorization, remote MCP transport, service principals and retention-aware account erasure require separate reviewed implementation. No user identity is synthesized for an external client, and no email-only ownership matching is used.
